## 결론 — 가이드에 꼭 반영할 것

1. **GitHub 공식 입문 시리즈가 SDLC 전 과정을 이미 보여 준다.** 「Start your journey」 7편이 저장소 → 계획(이슈·보드) → 내 컴퓨터로 가져오기 → 브랜치·커밋·PR → 리뷰·병합 → Pages 자동 배포 순서로 작은 웹 페이지를 끝까지 만든다(A-07~A-10). GitHub 은 SDLC 를 Plan·Create·Review·Test·Deploy·Operate 6단계로 나누고, 처음부터 다 쓸 필요는 없다고 한다(A-01~A-03).
2. **Claude Code 는 일을 "맥락 모으기 → 행동 → 결과 확인" 3단계 순환으로 설명한다**(A-04). "탐색 → 계획 → 코드 → 커밋" 4단계 표현은 현재 문서에서 **찾지 못했다**(확인 못 한 것 #1). 대신 편집 전에 계획을 먼저 보는 계획 모드가 있다(A-05).
3. **기획은 설치 없이 Claude Code 만으로 된다.** "나를 인터뷰해 SPEC.md 를 써 줘 → 새 세션에서 만들기 → 스펙과 대조해 리뷰"가 공식 모범 사례다(B-01~B-04). spec-kit(Python 3.11+·uv)·OpenSpec(설치 스크립트 또는 Node.js 22.12+)은 개념만 소개한다(B-09~B-18).
4. **테스트의 핵심은 "확인 장치"다.** 통과/실패로 답하는 검사를 주고(E-01~E-03), "다 통과했다"는 말 대신 **실행한 명령과 출력이라는 증거**를 요구한다(E-04).
5. **배포는 GitHub Pages, 무료 조건은 "공개 저장소"다**(F-02). 사이트 1GB·월 대역폭 100GB(느슨한 한도)·배포 10분 제한(F-05~F-07). 사업·쇼핑몰·SaaS 용으로 쓸 수 없고 비밀번호·카드번호 입력에 쓰면 안 된다(F-03, F-04). 방문자 IP 가 기록된다(F-09).
6. **실제 서비스를 흉내 낸 연습 사이트에는 조건이 붙는다.** 코드를 직접 쓰고, 사용자 데이터를 모으지 않고, 원본과 무관하다는 눈에 띄는 안내를 단다(F-08).
7. **비밀값은 절대 커밋하지 않는다.** 커밋하면 파일을 지워도 Git 기록에 남는다(H-03). 새면 **먼저 폐기·교체**한다(H-07, H-08). 공개 저장소로 올리려 하면 막는 사용자 푸시 보호가 기본으로 켜져 있다(H-05).
8. **되돌리기는 층이 다르다.** 체크포인트는 세션용이고 Git 을 대신하지 않는다(D-15). **배포처럼 바깥에 영향을 주는 행동은 체크포인트로 되돌릴 수 없다**(D-16).
9. **AI 리뷰는 판단을 대신하지 않는다.** 관리형 Code Review 는 PR 을 승인·차단하지 않고, "발견 없음"이 안전하다는 뜻도 아니다(D-11, D-12). 이 서비스는 **Team·Enterprise 전용**이라 개인 독자는 `/code-review` 를 쓴다(D-13, D-14).

# A. SDLC 와 AI

## A.1 GitHub 이 말하는 SDLC

**A-01** SDLC(소프트웨어 개발 생애 주기)는 처음 아이디어부터 실제로 돌아가는 코드까지 프로젝트가 거치는 단계를 말한다. GitHub 은 그 모든 단계를 돕도록 만들어졌다고 소개한다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/what-is-github · 확인일 2026-11-01
> "The software development life cycle describes the stages a software project moves through, from the first idea to running code in production."

**A-02** 여섯 단계와 GitHub 에서 하는 일(표 칸 원문). Plan = 할 일 추적·마일스톤·장기 계획 / Create = 코드 쓰고 저장, 새 기능을 안전하게, 변경의 시간 순서 기록 / Review = 변경 제안·리뷰어와 논의·피드백 반영 / Test = 병합 전 모든 변경을 자동 검사 / Deploy = 자동 배포·릴리스 관리 / Operate = 운영 감시·의존성 관리·보안 문제 찾아 고치기. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/what-is-github · 확인일 2026-11-01
> "Track your work, set milestones, and organize long-term projects."
> "Write and store code, develop new features safely, and create a clear timeline of your changes."
> "Suggest changes to your project, discuss your updates with reviewers, and apply feedback."
> "Automate checks to validate every change before it merges."
> "Ship software with automated deployment workflows and release management."
> "Monitor applications, manage dependencies, and find and fix security issues."

**A-03** 모든 단계를 한꺼번에 쓸 필요는 없다. 저장소 하나와 이슈 몇 개로 시작해 늘려 가는 사람이 많다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/what-is-github · 확인일 2026-11-01
> "You do not need to use every stage at once. Many people start with a repository and a few issues, then expand their use of the platform as their project grows."

## A.2 Claude Code 가 일하는 방식

**A-04** Claude Code 는 일을 맥락 모으기(gather context) → 행동하기(take action) → 결과 확인하기(verify results) 세 단계로 한다. 세 단계는 섞여 돌아가고, 테스트를 돌려 자기 일을 확인하는 것도 그 안에 들어 있다. — VERIFIED · https://code.claude.com/docs/en/how-claude-code-works · 확인일 2026-11-01
> "When you give Claude a task, it works through three phases: **gather context**, **take action**, and **verify results**."
> "Claude uses tools throughout, whether searching files to understand your code, editing to make changes, or running tests to check its work."

**A-05** 편집 전에 검토하고 싶은 변경은 계획 모드(plan mode)로 바꾼다. Claude 가 파일을 읽고 계획을 내놓지만, 승인하기 전에는 아무것도 고치지 않는다. — VERIFIED · https://code.claude.com/docs/en/common-workflows · 확인일 2026-11-01
> "For changes you want to review before they touch disk, switch to plan mode. Claude reads files and proposes a plan but makes no edits until you approve."

**A-06** 모범 사례 문서는 세션이 기대대로 안 갈 때의 대표 원인을 넷으로 꼽는다. 그중 둘이 SDLC 와 직결된다. 하나는 저장소만 읽어서는 알 수 없는 정보가 빠진 것(→ 기획·명세), 다른 하나는 스스로 확인할 방법이 없었던 것(→ 테스트)이다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "Claude built something different from what you had in mind, or it has to rediscover the same fact at the start of every session. It's missing information it can't get from reading the repo."
> "Claude said it was done and it wasn't quite, usually because it had no way to check its own work."

## A.3 GitHub 공식 입문 시리즈 「Start your journey」

**A-07** 시리즈는 `stargazers-log` 라는 작은 웹사이트를 만든다. 끝까지 따라 하면 계획하고, 코드를 쓰고, 변경을 리뷰하고, 실제 웹사이트로 배포하게 된다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/creating-a-repository-for-your-project-on-github · 확인일 2026-11-01
> "By the end of the journey, you'll plan work, write code, review changes, and deploy your code to a live website."

**A-08** 시리즈 마지막 편이 정리한 단계와 배운 것(표 칸 원문). 프로젝트 만들기 = 저장소·README / 계획 = 이슈·프로젝트 보드 / 내 컴퓨터와 연결 = GitHub Desktop·복제 / 코드 쓰고 저장 = 브랜치·커밋·PR / 리뷰 = PR 리뷰 / 자동 배포 = Actions·Pages. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/deploying-your-website-automatically · 확인일 2026-11-01
> "Repositories, README files"
> "Issues, Projects (project boards)"

**A-09** 코드를 쓰는 편은 핵심 개발 흐름을 "작업 공간 만들기 → 변경하고 저장하기 → 리뷰 받으려고 제안하기"로 요약한다. 그 도구가 브랜치·커밋·PR 이다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/writing-and-storing-your-code · 확인일 2026-11-01
> "Along the way, you'll follow the core developer workflow—setting up a space for your work, making and saving your changes, and proposing them for review—using branches, commits, and a pull request."

**A-10** AI 가 만든 코드는 검토하고 나서 고친다. 튜토리얼은 AI(Copilot)가 만든 것을 검토한 뒤 예시에 맞게 조정하라고 한다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/writing-and-storing-your-code · 확인일 2026-11-01
> "Review what {% data variables.product.prodname_copilot_short %} generates, then adjust the files to match the examples below."

## A.4 GitHub flow(브랜치 중심 작업 흐름)

**A-11** GitHub flow 는 가벼운 브랜치 중심 작업 흐름이다. 개발자만이 아니라 누구에게나 쓸모 있다고 한다. — VERIFIED · https://docs.github.com/en/get-started/using-github/github-flow · 확인일 2026-11-01

> "Don't worry about losing information. Your pull request and commit history will not be deleted."

# B. 기획·요구사항·명세

## B.1 Claude Code 만으로 하는 기획(설치 불필요)

**B-01** 원하는 것이 아직 분명하지 않으면, 프롬프트를 쓰기 전에 다 정리할 필요가 없다. Claude 에게 나를 인터뷰하게 한다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "When you don't know exactly what you want yet, you don't have to work it all out before you prompt. Ask Claude to interview you instead:"

**B-02** 문서의 예시 프롬프트. 스펙을 쓸 수 있을 때까지 인터뷰하고 SPEC.md 에 적게 한다. Claude 는 정하지 않은 부분을 객관식 질문으로 묻는다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "I want to add rate limiting to the public API but haven't thought it through yet. Interview me until you could write the spec, then write it to SPEC.md."
> "Claude comes back with multiple-choice questions about the parts you haven't pinned down: per-user versus per-key limits, what happens to requests over the limit, what's out of scope."

**B-03** SPEC.md 가 생기면 새 세션에서 그것으로 만든다. 깨끗한 맥락과 글로 적힌 "완료의 정의"로 시작하기 위해서다. 나중에 리뷰어에게 보여 줄 기준 파일도 이것이다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done."

**B-04** 다 만든 뒤에는 스펙과 대조해 리뷰하게 한다. 예시 프롬프트 끝의 "스타일은 건너뛰라(skip style)"는 빼지 말라고 한다. 문제를 찾으라고 하면 리뷰어는 늘 뭔가를 찾아내고, 그걸 다 고치면 쓸데없는 층과 일어날 수 없는 경우의 테스트가 생긴다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style"
> "A reviewer that's asked to find problems will always find *something*."

**B-05** 구체적인 프롬프트가 수정 왕복을 줄인다. 파일을 짚고, 증상을 말하고, "고쳐졌다"가 어떤 모습인지 처음에 말하라. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "If you name the file, describe the symptom, and say what "fixed" looks like up front, you usually save yourself a round of corrections later."

**B-06** 아쉬운 예와 나은 예(표 원문). "로그인 버그 고쳐" 대신 증상·위치·실패하는 테스트 먼저 쓰기까지 말한다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "*"users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"*"

## B.2 GitHub 이 보여 주는 "계획" 단계

**B-07** 코드를 쓰기 전에 만들 것을 적어 두고 진행을 추적한다. 튜토리얼은 이것을 이슈와 프로젝트 보드로 한다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/planning-your-work · 확인일 2026-11-01
> "Before you write code, capture what you want to build and track your progress."

**B-08** 첫 이슈의 예. 제목은 "별표한 저장소 목록 보여 주기", 설명에는 만들고 싶은 것을 몇 줄 적는다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/planning-your-work · 확인일 2026-11-01
> "In the **Add a title** field, type `Display a list of starred repositories`."

## B.3 spec-kit(GitHub 의 스펙 주도 개발 도구)

**B-09** spec-kit 은 AI 코딩 에이전트에게 정해진 절차·재사용 템플릿·기록되는 결과물을 주는 오픈소스 도구 모음이다. — VERIFIED · https://github.com/github/spec-kit · 확인일 2026-11-01
> "Spec Kit is an open source toolkit that gives AI coding agents structured processes, reusable templates, and documented outcomes."

**B-10** 스펙 주도 개발(Spec-Driven Development)은 무엇을 왜 만들지 먼저 정하고, 그 명세를 계획·작업·동작하는 코드로 바꾸는 것이다. — VERIFIED · https://github.com/github/spec-kit · 확인일 2026-11-01
> "Define what to build and why, then turn the specification into a plan, tasks, and working code."

**B-11** 헌법(constitution)은 프로젝트마다 한 번 만들고, 나머지 단계는 기능마다 반복한다. 각 단계는 터미널이 아니라 **에이전트 채팅창**에서 하나씩, 결과를 검토하고 넘어간다. — VERIFIED · https://github.com/github/spec-kit · 확인일 2026-11-01
> "Create a constitution once per project and repeat the remaining steps for each feature. Run these skills in your agent's chat, not your terminal, one at a time, reviewing each result before continuing."

**B-12** 헌법 단계는 프로젝트의 기본 원칙을 정한다. 이후 모든 단계가 이 원칙에 비추어 평가된다. — VERIFIED · https://github.com/github/spec-kit/blob/main/docs/quickstart.md · 확인일 2026-11-01
> "Establishes the project's guiding principles, which every later step is evaluated against."

**B-13** 명세(specify) 단계는 평소 말로 쓴 설명에서 기능 명세를 만든다. 기술 스택이 아니라 **무엇을, 왜**에 집중한다. 기술 선택은 계획(plan) 단계에서 한다. — VERIFIED · https://github.com/github/spec-kit/blob/main/docs/quickstart.md · 확인일 2026-11-01
> "Creates the feature specification from a natural-language description. Focus on the **what** and **why**, not the tech stack."
> "Generates the design artifacts from the spec. This is where implementation detail belongs — provide your tech stack and architecture."

**B-14** 명확화(clarify) 단계는 덜 정해진 것을 콕 집어 묻고 답을 명세에 다시 넣는다. 작업(tasks) 단계는 의존 순서대로 정렬된 `tasks.md` 를 만든다. 짧은 경로는 specify → plan → tasks → implement → converge 다. — VERIFIED · https://github.com/github/spec-kit/blob/main/docs/quickstart.md · 확인일 2026-11-01
> "Asks targeted questions about anything underspecified and folds your answers back into the spec, so you're not planning on top of ambiguity."
> "Generates an actionable, dependency-ordered `tasks.md` from the design artifacts."

**B-15** 설치 요건. Python 3.11 이상, uv, 지원되는 AI 코딩 에이전트가 필요하다. 지원 에이전트 목록에 Claude Code 가 있다. Git 은 git 확장을 켤 때만 필요하다. — VERIFIED · https://github.com/github/spec-kit · 확인일 2026-11-01
> "You need Python 3.11+, [uv](https://github.github.io/spec-kit/install/uv.html), and a supported AI coding agent on Linux, macOS, or Windows."

## B.4 OpenSpec(가벼운 스펙 층)

**B-16** OpenSpec 은 요구사항이 채팅 기록에만 있으면 AI 가 예측하기 어렵다는 문제에서 출발한다. 코드를 쓰기 전에 무엇을 만들지 합의하는 가벼운 스펙 층을 더한다. — VERIFIED · https://github.com/Fission-AI/OpenSpec · 확인일 2026-11-01
> "AI coding assistants are powerful but unpredictable when requirements live only in chat history. OpenSpec adds a lightweight spec layer so you agree on what to build before any code is written."

**B-17** 변경마다 폴더가 하나 생기고, 그 안에 제안(proposal, 왜·무엇을)·명세(specs, 요구사항과 시나리오)·설계(design)·작업 목록(tasks)이 든다. AI 가 이것을 쓰고, 사람은 코드가 쓰이기 전에 계획을 검토한다. — VERIFIED · https://github.com/Fission-AI/OpenSpec · 확인일 2026-11-01
> "**Stay organized** — each change gets its own folder with proposal, specs, design, and tasks"
> "Your AI writes these; you review the plan before any code is written."

**B-18** 명세는 "구현 계획"이 아니라 "동작 약속(behavior contract)"이다. 구현을 바꿔도 밖에서 보이는 동작이 안 바뀐다면 그 내용은 명세에 넣지 않는다. 설치는 터미널 설치 스크립트 또는 Node.js 22.12 이상이 필요한 npm 이다(H-13 의 주의 참고). — VERIFIED · https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md · 확인일 2026-11-01
> "A spec is a **behavior contract**, not an implementation plan."
> "If implementation can change without changing externally visible behavior, it likely does not belong in the spec."

# C. GitHub 저장소 기초

## C.1 저장소와 GitHub·Git

**C-01** 저장소(repository)는 소프트웨어 프로젝트의 코드와 파일을 GitHub 에 두는 곳이다. 파일을 보관하고, 바뀔 때마다 커밋으로 기록하고, 함께 일할 공간이 된다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/creating-a-repository-for-your-project-on-github · 확인일 2026-11-01
> "It stores your files, tracks each change as a commit, and gives collaborators a shared place to work."

**C-02** Git 은 파일 변경을 추적하는 버전 관리 시스템이다. GitHub 은 Git 프로젝트(저장소)를 클라우드에 올려 두고 계획·협업 도구를 더한 것이다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/what-is-github · 확인일 2026-11-01
> "Git is a version control system that tracks changes to files."

**C-03** 저장소 용어(표 원문). 브랜치 = 저장소 안의 평행한 코드 버전으로 main 에 영향을 주지 않음 / 복제(clone) = 모든 파일의 모든 버전까지 통째로 내려받기 / 병합(merge) = 한 브랜치의 변경을 다른 브랜치에 적용 / 원격(remote) = 내 컴퓨터가 아니라 GitHub 에 있는 저장소. — VERIFIED · https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories · 확인일 2026-11-01
> "Branch | A parallel version of your code that is contained within the repository, but does not affect the primary or main branch."
> "Merge | To take the changes from one branch and apply them to another."
> "Remote | A repository stored on {% data variables.product.github %}, not on your computer."

## C.2 공개와 비공개

**C-04** 공개 저장소는 인터넷의 누구나 볼 수 있다. 비공개 저장소는 나와 내가 명시적으로 공유한 사람만 볼 수 있다. — VERIFIED · https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories · 확인일 2026-11-01
> "Public repositories are accessible to everyone on the internet."
> "Private repositories are only accessible to you, people you explicitly share access with, and, for organization repositories, certain organization members."

**C-05** 공개 저장소는 코드 전체를 모두에게 보여 주므로 공격자가 약점이나 민감한 정보를 노릴 위험이 커진다. 문서는 Dependabot·비밀값 검사·푸시 보호 같은 보안 기능을 켜라고 권한다. — VERIFIED · https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories · 확인일 2026-11-01
> "Public repositories expose your codebase to everyone, increasing the risk that attackers might exploit vulnerabilities or access sensitive information."

**C-06** 튜토리얼은 나중에 실제 사이트로 내보내기 위해 공개(Public)를 고르게 한다(무료 플랜의 Pages 조건은 F-02). — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/creating-a-repository-for-your-project-on-github · 확인일 2026-11-01
> "Use the **Choose visibility** dropdown menu to select **Public** so you can publish your software project to a live site later in this series."

**C-07** 무료 플랜에서 공개 저장소를 비공개로 바꾸면 일부 기능이 사라지고, 게시된 Pages 사이트는 자동으로 게시가 내려간다. 비공개를 공개로 바꾸면 Actions 기록과 로그가 모두에게 보인다. — VERIFIED · https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility · 확인일 2026-11-01
> "Any published {% data variables.product.prodname_pages %} site will be automatically unpublished."
> "Actions history and logs will be visible to everyone."

## C.3 저장소 만들기와 README·.gitignore·라이선스

**C-08** 새 저장소를 만들 때 README·`.gitignore`·라이선스를 함께 넣을 수 있다. 단, 이미 있는 저장소를 들여올 때는 병합 충돌이 날 수 있으니 고르지 말라고 한다. — VERIFIED · https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository · 확인일 2026-11-01
> "If you're importing an existing repository to {% data variables.product.github %}, don't choose any of these options, as you may introduce a merge conflict."

**C-09** 튜토리얼은 **Add README** 를 고르게 한다. 시작 파일이자 프로젝트를 설명하는 자리가 된다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/creating-a-repository-for-your-project-on-github · 확인일 2026-11-01
> "Select **Add README**. This gives your repository a starting file and a place to describe your software project."

**C-10** README 는 방문자가 가장 먼저 보는 경우가 많다. 보통 무엇을 하는지·왜 쓸모 있는지·어떻게 시작하는지·어디서 도움을 받는지·누가 관리하는지를 적는다. — VERIFIED · https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes · 확인일 2026-11-01
> "A README is often the first item a visitor will see when visiting your repository."
> "What the project does"

**C-11** `.gitignore` 는 커밋할 때 Git 이 무시할 파일·폴더를 알려 준다. GitHub 은 언어·환경별 추천 `.gitignore` 목록(github/gitignore)을 관리한다. — VERIFIED · https://docs.github.com/en/get-started/git-basics/ignoring-files · 확인일 2026-11-01
> "You can create a `.gitignore` file in your repository's root directory to tell Git which files and directories to ignore when you make a commit."

**C-12** 이미 커밋된 파일은 `.gitignore` 에 적기만 해서는 무시되지 않는다. 먼저 추적을 풀어야 한다(`git rm --cached`). 비밀값 파일을 늦게 무시 목록에 넣는 실수와 연결된다(H 묶음). — VERIFIED · https://docs.github.com/en/get-started/git-basics/ignoring-files · 확인일 2026-11-01
> "If you want to ignore a file that is already checked in, you must untrack the file before you add a rule to ignore it."

**C-13** 라이선스는 다른 사람이 내 코드로 무엇을 할 수 있고 없는지 알려 준다. 고를 의무는 없지만, 없으면 기본 저작권법이 적용되어 아무도 복제·배포·2차 저작을 할 수 없다. 고르는 데는 choosealicense.com 을 권한다. — VERIFIED · https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository · 확인일 2026-11-01
> "A software license tells others what they can and can't do with your source code, so it's important to make an informed decision."
> "However, without a license, the default copyright laws apply, meaning that you retain all rights to your source code and no one may reproduce, distribute, or create derivative works from your work."

**C-14** GitHub 은 자신들이 변호사가 아니며 실수할 수 있다고 면책 문구를 단다. 라이선스 장에서는 "법률 조언이 아니다"를 같이 적는다. — VERIFIED · https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository · 확인일 2026-11-01
> "We hope it helps, but please keep in mind that we’re not lawyers and that we make mistakes like everyone else."

## C.4 내 컴퓨터와 연결하기

**C-15** 복제(clone)는 내 컴퓨터에 저장소 사본을 만들되 GitHub 의 원본과 연결된 채로 둔다. 튜토리얼은 GitHub Desktop 으로 복제한다. GitHub Desktop 은 무료 오픈소스 앱이고 그래픽 화면이라 Git 명령어보다 쉬울 수 있다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/connecting-to-your-code-locally · 확인일 2026-11-01
> "Cloning creates a copy of your repository on your computer that stays connected to the version on {% data variables.product.github %}."

**C-16** 이미 내 컴퓨터에 있는 폴더(Git 으로 관리 중이든 아니든)도 GitHub 에 올릴 수 있다. Git 으로 관리하지 않는 폴더라면 먼저 Git 저장소로 초기화한다. 3단계 「정리도구」 폴더가 이 경우다. — VERIFIED · https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github · 확인일 2026-11-01
> "If your locally-hosted code isn't tracked by any VCS, the first step is to initialize a Git repository."

# D. 브랜치·커밋·PR·코드 리뷰

## D.1 브랜치와 커밋

**D-01** 브랜치는 기능을 따로 떨어진 공간에서 만들게 해 준다. 준비될 때까지 `main` 은 바뀌지 않는다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/writing-and-storing-your-code · 확인일 2026-11-01
> "A branch lets you work on your feature in its own space, without changing the `main` copy of your code until you're ready."

**D-02** 브랜치 이름은 짧고 뜻이 드러나게 짓는다(예: `increase-test-timeout`). 브랜치는 안전한 작업 공간이고, 병합하기 전에는 기본 브랜치에 들어가지 않는다. — VERIFIED · https://docs.github.com/en/get-started/using-github/github-flow · 확인일 2026-11-01
> "A short, descriptive branch name enables your collaborators to see ongoing work at a glance."

**D-03** 커밋은 변경의 스냅숏(그 순간의 사진)을 저장하고, 푸시는 그것을 GitHub 저장소로 보낸다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/writing-and-storing-your-code · 확인일 2026-11-01
> "Committing saves a snapshot of your changes, and pushing sends them to {% data variables.product.github %} where they will be stored in your repository."

**D-04** 커밋 하나에는 따로 떨어진 완결된 변경 하나를 담는 것이 좋다. 그래야 나중에 그 부분만 되돌리기 쉽다. 서로 관계없는 변경은 브랜치도 따로 만든다. — VERIFIED · https://docs.github.com/en/get-started/using-github/github-flow · 확인일 2026-11-01
> "Ideally, each commit contains an isolated, complete change. This makes it easy to revert your changes if you decide to take a different approach."
> "Make a separate branch for each set of unrelated changes."

## D.2 풀 리퀘스트(PR)

**D-05** PR 은 한 브랜치의 변경을 다른 브랜치에 병합하자고 제안하는 것이다. 프로젝트에 들어가기 전에 논의하고 검토할 자리를 준다. — VERIFIED · https://docs.github.com/en/pull-requests/get-started/about-pull-requests · 확인일 2026-11-01
> "A pull request proposes merging code changes from one branch into another. As a collaborative feature, pull requests give you a place to discuss and review work before it becomes part of a project."

**D-06** PR 화면의 주요 부분. Conversation(설명·댓글·리뷰), Commits(브랜치가 바뀐 과정), Checks(자동 테스트·빌드 결과), Files changed(리뷰어가 댓글을 다는 차이). — VERIFIED · https://docs.github.com/en/pull-requests/get-started/about-pull-requests · 확인일 2026-11-01
> "**Checks** shows the results of automated tests, builds, and other validations."
> "**Files changed** shows the diff that reviewers comment on."

**D-07** PR 을 만들 때는 변경 요약과 어떤 문제를 푸는지 적는다. 이슈를 해결하는 PR 이면 이슈를 연결한다. 키워드로 연결하면 PR 이 병합될 때 이슈가 자동으로 닫힌다. — VERIFIED · https://docs.github.com/en/get-started/using-github/github-flow · 확인일 2026-11-01
> "When you create a pull request, include a summary of the changes and what problem they solve."
> "If you link with a keyword, the issue will close automatically when the pull request merges."

**D-08** 작은 PR 이 리뷰하기 쉽고 병합하기 안전하다. 커지면 목적 하나씩으로 쪼갠다. 남에게 리뷰를 부탁하기 전에 먼저 스스로 검토한다(차이 읽기, 실수로 바꾼 것 찾기, 빌드·테스트가 돌았는지 확인). — VERIFIED · https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes · 확인일 2026-11-01
> "Small, focused pull requests are easier to review and safer to merge."
> "A self-review can include reading the diff, checking for accidental changes, and making sure relevant builds or tests have run."

## D.3 리뷰

**D-09** 혼자 일해도 병합 전에 의도적으로 리뷰하는 습관은 프로젝트를 건강하게 하고 나중의 협업을 쉽게 한다. 튜토리얼은 Files changed 탭에서 버그·빠진 오류 처리·접근성 문제·나중에 읽을 사람이 헷갈릴 부분을 보라고 한다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/reviewing-your-proposed-changes · 확인일 2026-11-01
> "Even when you work alone, a deliberate review builds a habit that keeps your software projects healthy and makes collaboration easier later."

**D-10** 리뷰의 세 가지 결정. Comment(의견만), Approve(병합 준비됨), Request changes(병합 전에 고쳐야 함). — VERIFIED · https://docs.github.com/en/pull-requests/get-started/reviewing-pull-requests-quickstart · 확인일 2026-11-01
> "**Approve** signals that the changes are ready to merge."
> "**Request changes** flags feedback the author must address before merging."

# E. 테스트와 자동 검사

## E.1 Claude 에게 "확인 장치"를 준다

**E-01** Claude 는 일이 끝나 보이면 멈춘다. 실제로 끝났는지 알려 줄 실행 장치가 없으면, 결국 사람이 테스트 역할을 하게 된다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, "looks done" is all it has to go on."
> "In practice that makes you the test suite, and every mistake sits there until you happen to notice it."

**E-02** 통과/실패로 답하는 것을 주면 Claude 가 스스로 고리를 닫는다. 바꾸고, 검사를 돌리고, 깨졌으면 출력을 읽고 고쳐 다시 돌린다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "If you give it something that comes back pass or fail, Claude can close that loop itself."

**E-03** 검사는 Claude 가 결과를 읽을 수 있으면 무엇이든 된다(테스트 파일, 빌드 종료 코드, 린터, 출력 비교 스크립트, 시안 옆의 브라우저 스크린샷). 그런 것이 있다면 CLAUDE.md 에서 가장 쓸모 있는 한 줄은 그것을 돌리는 명령이다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "If your repo already has one of these, the single most useful line in your `CLAUDE.md` is the command that runs it."

**E-04** 어떤 방법을 쓰든 **증거**를 달라고 한다. 실행한 명령과 그 출력, 또는 스크린샷이다. "다 통과했다"는 말만으로는 알 수 있는 게 거의 없다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "Whichever option you use, ask Claude for *evidence*: the command it ran and its output, or the screenshot. "All tests pass" on its own tells you very little, and reading the output is faster than rerunning the check yourself."

**E-05** 가장 쉬운 방법은 프롬프트에 적는 것이다("끝나면 auth 테스트를 돌리고, 통과할 때까지 계속해"). 설정 없이 오늘 바로 된다. — VERIFIED · https://code.claude.com/docs/en/best-practices · 확인일 2026-11-01
> "In the prompt: `run the auth tests after, and keep going until they pass`. Claude decides for itself when it's satisfied."

**E-06** 테스트 작성 순서(절 제목 원문): 테스트 안 된 코드 찾기 → 테스트 뼈대 만들기 → 의미 있는 경우 추가 → 돌리고 확인. 테스트를 부탁할 때는 어떤 동작을 확인할지 구체적으로 말한다. — VERIFIED · https://code.claude.com/docs/en/common-workflows · 확인일 2026-11-01
> "When asking for tests, be specific about what behavior you want to verify."

**E-07** 데스크톱 앱은 개발 서버를 켜고 브라우저 창(Browser pane)에서 열어 자기 변경을 확인할 수 있다. 기본으로 편집할 때마다 자동 확인(auto-verify)한다. — VERIFIED · https://code.claude.com/docs/en/desktop · 확인일 2026-11-01
> "Claude can start a dev server and open it in the Browser pane to verify its changes."

> "The job must have a minimum of `pages: write` and `id-token: write` permissions."

# G. 운영과 개선

**G-01** 이슈(issue)는 계획하고 논의하고 할 일을 추적하는 기록이다. 버그 신고, 새 기능·아이디어 등 적어 두거나 논의할 것은 무엇이든 담는다. — VERIFIED · https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues · 확인일 2026-11-01
> "You can create issues in your repository to plan, discuss, and track work."

**G-02** 이슈는 PR 과 이어진다. PR 에 `fixes` 같은 키워드를 쓰면 관련 이슈가 자동으로 닫힌다. — VERIFIED · https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues · 확인일 2026-11-01
> "Mentioning an issue in another issue or pull request will create references between them and using keywords, like `fixes:`, in your pull requests will automatically close the associated issues."

**G-03** 라벨(label)로 이슈와 PR 을 분류한다. 새 저장소에는 기본 라벨이 들어 있다. 예: `bug`(예상치 못한 문제), `enhancement`(새 기능 요청), `documentation`(문서 개선). — VERIFIED · https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels · 확인일 2026-11-01
> "{% data variables.product.github %} provides default labels in every new repository."
> "`bug` | Indicates an unexpected problem or unintended behavior"

**G-04** 프로젝트(Projects)는 이슈·PR 과 이어진 표·보드·로드맵이다. 바꾼 내용이 양쪽으로 자동 동기화된다. — VERIFIED · https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects · 확인일 2026-11-01
> "A project is an adaptable table, board, and roadmap that integrates with your issues and pull requests on {% data variables.product.company_short %} to help you plan and track your work effectively at the user or organization level."

**G-05** 튜토리얼의 보드는 열이 일의 단계를 나타낸다(Todo → In Progress → Done). 기능이 배포되면 Done 으로 옮긴다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/planning-your-work · 확인일 2026-11-01
> "The board's columns represent stages of your work. As you make progress, move each item to show its status."

**G-06** 한 바퀴가 끝나면 다음 기능을 새 이슈로 만들고, 시작할 때 In Progress 로 옮겨 다음 순환을 시작한다. — VERIFIED · https://docs.github.com/en/get-started/start-your-journey/reviewing-your-proposed-changes · 확인일 2026-11-01
> "If you have more features to build, create new issues and move them to **In Progress** when you start the next cycle."

**G-07** 릴리스(release)는 더 많은 사람이 내려받아 쓸 수 있게 묶은 배포 단위다. Git 태그(기록의 특정 지점 표시)를 바탕으로 한다. 웹 페이지 하나짜리 실습에는 필수가 아니다(필자 판단). — VERIFIED · https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases · 확인일 2026-11-01
> "Releases are deployable software iterations you can package and make available for a wider audience to download and use."

# H. 안전과 책임

## H.1 비밀값(시크릿)

**H-01** 비밀번호나 API 키 같은 민감한 정보는 절대 `git add`·`commit`·`push` 하지 않는다(공통 문단). — VERIFIED · https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github · 확인일 2026-11-01
> "Never `git add`, `commit`, or `push` sensitive information, for example passwords or API keys, to a remote repository."

**H-02** 비밀값은 민감한 시스템과 데이터에 접근하게 해 주는 자격 증명이다. 예: 외부 서비스용 API 키·토큰, 데이터베이스 비밀번호. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/secret-leakage-risks · 확인일 2026-11-01
> "Secrets are credentials that grant access to sensitive systems and data."
> "API keys and tokens used to authenticate with external services"

**H-03** 커밋된 비밀값은 Git 기록의 일부가 되어 최신 커밋에서 지워도 남는다. 그래서 유출을 해결하려면 파일 삭제로는 부족하다. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/secret-leakage-risks · 확인일 2026-11-01
> "These hardcoded secrets become part of your Git history and remain accessible even after being removed from the latest commit."

**H-04** 비밀값이 새는 흔한 경로: 로컬에서 시험하다 넣은 값을 실수로 커밋, `.env` 같은 설정 파일, 문서·README 의 예시에 진짜 키. 공개 저장소의 비밀값은 검색 엔진과 전문 스캐너에 수집된다. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/secret-leakage-risks · 확인일 2026-11-01
> "Secrets in configuration files such as `.env` files or infrastructure-as-code templates"
> "Public repositories with exposed secrets are indexed by search engines and specialized scanning services."

**H-05** 푸시 보호(push protection)는 비밀값이 담긴 푸시를 저장소에 닿기 **전에** 막는다. "사용자용 푸시 보호"는 내 GitHub 계정에 기본으로 켜져 있고, 공개 저장소로 비밀값을 올리지 못하게 한다. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/push-protection · 확인일 2026-11-01
> "Rather than alerting you to credential leaks after the fact, push protection blocks pushes that contain secrets _before_ they reach your repository."
> "Stops you from pushing secrets to public repositories on {% data variables.product.github %}"

**H-06** 비밀값 검사(secret scanning)는 저장소의 모든 브랜치·전체 Git 기록에서 하드코딩된 자격 증명을 찾는다. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning · 확인일 2026-11-01
> "{% data variables.product.prodname_secret_scanning_caps %} scans your entire Git history on all branches of your repository for hardcoded credentials, including API keys, passwords, tokens, and other known secret types."

**H-07** 경고를 받으면 그 자격 증명을 **즉시 교체(rotate)**한다. Git 기록에서 지우는 일은 시간이 많이 들고, 이미 폐기했다면 대개 필요 없다. — VERIFIED · https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning · 확인일 2026-11-01
> "When you receive an alert, rotate the affected credential immediately to prevent unauthorized access."

**H-08** 지울 것이 비밀값이라면 첫 단계는 폐기·교체다. 기록 다시 쓰기(history rewrite)는 협업자 조율이 필요하고 부작용이 많다. — VERIFIED · https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository · 확인일 2026-11-01
> "It is important to note that if the sensitive data you need to remove is a secret (e.g. password/token/credential), as is often the case, then as a first step you need to revoke and/or rotate that secret."

**H-09** 워크플로에 비밀값이 필요하면 GitHub Actions 의 "Secrets"에 넣는다. Actions 는 워크플로에 명시한 비밀값만 읽을 수 있다. — VERIFIED · https://docs.github.com/en/actions/concepts/security/secrets · 확인일 2026-11-01
> "{% data variables.product.prodname_actions %} can only read a secret if you explicitly include the secret in a workflow."

**H-10** Claude Code GitHub Actions 문서도 같은 경고를 한다. API 키나 OAuth 토큰을 저장소에 직접 커밋하지 말고 GitHub Secrets 에 넣어 참조한다. — VERIFIED · https://code.claude.com/docs/en/github-actions · 확인일 2026-11-01
> "Never commit API keys or OAuth tokens directly to your repository."

**H-11** Claude Code 에서 `.env` 같은 파일을 아예 못 읽게 하려면 `Read` 거부 규칙을 넣는다(예: `Read(./.env)`). `.claudeignore` 파일은 효과가 없다. — VERIFIED · https://code.claude.com/docs/en/permissions · 확인일 2026-11-01
> "To block Claude's file tools from reading a file or directory, add a `Read` deny rule for its path, such as `Read(./.env)` or `Read(./secrets/**)`;"

## H.2 권한과 책임

**H-12** 제안된 코드와 명령을 승인하기 전에 안전한지 검토할 책임은 사용자에게 있다. — VERIFIED · https://code.claude.com/docs/en/security · 확인일 2026-11-01
> "You're responsible for reviewing proposed code and commands for safety before approval."

**H-13** 도구 설치의 주의. OpenSpec README 는 설치 방법으로 내려받은 스크립트를 셸에 바로 넘기는 명령(`curl … | sh`)을 먼저 보여 준다. 이 가이드에서는 이런 설치를 독자에게 시키지 않고 개념만 소개한다(필자 판단). 또 OpenSpec 은 익명 사용 통계를 모으며 끄는 방법을 적어 두었다. — VERIFIED · https://github.com/Fission-AI/OpenSpec · 확인일 2026-11-01
> "curl -fsSL https://openspec.dev/cli/install.sh | sh"
> "OpenSpec collects anonymous usage stats."

## H.3 의존성·AI 출력물·데이터

**H-14** Dependabot 은 내가 쓰는 패키지(의존성)에 알려진 취약점이 있으면 경고한다. 저장소의 기본 브랜치를 살피고, 경고에는 영향받는 파일·심각도·고쳐진 버전(있으면)이 들어 있다. — VERIFIED · https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts · 확인일 2026-11-01
> "Software often relies on packages from various sources, creating dependency relationships that can unknowingly introduce security vulnerabilities."

**H-15** AI 출력물의 권리와 데이터 사용. Anthropic 소비자 약관(시행 2025-10-08 표시)은 약관을 지키는 조건으로, 출력물(Outputs)에 대해 Anthropic 이 가진 권리를 "있다면" 사용자에게 넘긴다고 한다. 이것은 "AI 가 만든 코드에 저작권이 생기는가"에 대한 답은 아니다(확인 못 한 것 #2). Claude Code 문서는 Free·Pro·Max·Ultra 계정에서 설정이 켜져 있으면 데이터(Claude Code 사용 포함)를 모델 학습에 쓴다고 적는다. — VERIFIED · https://www.anthropic.com/legal/consumer-terms · https://code.claude.com/docs/en/data-usage · 확인일 2026-11-01
> "Subject to your compliance with our Terms, we assign to you all of our right, title, and interest—if any—in Outputs."
> "We will train new models using data from Free, Pro, Max, and Ultra accounts when this setting is on (including when you use Claude Code from these accounts)."

# 가이드 목차에 주는 시사점

공식 근거가 튼튼한 순서로 적었다.

1. **뼈대는 GitHub 「Start your journey」 7편을 따른다**(A-07~A-10, F-13). 예제가 목록을 보여 주는 정적 웹 페이지라 「할 일 보드」와 구조가 같다. AI 자리만 Copilot 대신 Claude Code 로 바꾼다.
2. **SDLC 개념 장 = GitHub 6단계 표 + Claude Code 3단계 순환**(A-01~A-04). "처음부터 다 쓸 필요 없다"(A-03)는 부담 덜기 문장으로 바로 쓴다.
3. **기획 장의 중심은 설치 없는 "인터뷰 → SPEC.md → 새 세션 → 스펙 대조 리뷰"**(B-01~B-04). spec-kit·OpenSpec 은 한 절로 개념만 다루고(B-09~B-18), 설치는 시키지 않는다.
4. **테스트 장은 "확인 장치를 주고 증거를 받는다"**(E-01~E-05). 첫 실습은 데스크톱 앱 브라우저 미리보기 확인(E-07), 다음 절에 Actions 자동 테스트(E-08~E-10).
5. **저장소 장은 공개/비공개를 배포와 묶어 설명한다**(C-04~C-07, F-02). README·`.gitignore`·라이선스는 공식 문장이 짧고 분명하다(C-09~C-14).
6. **브랜치·PR·리뷰 장은 GitHub flow + PR·리뷰 퀵스타트로 충분하다**(A-11, A-12, D-01~D-10). Claude Code 쪽은 diff 댓글·`/code-review`·PR 모니터링(D-14, D-17~D-19). 관리형 Code Review 는 Team·Enterprise 전용이라 언급만(D-13).
7. **배포 장에 Pages 한도·금지 사항 상자를 둔다**(F-03~F-09). 교육용 복제 조건(F-08)은 실습 UI 원칙과 같은 이야기다. 방문자 IP 기록(F-09)은 첫 화면의 「모으지 않습니다」 약속과 맞춰 본다.
8. **되돌리기·책임 절은 배포 직전에 둔다**(D-15, D-16, H-12). "배포는 사람이 확인하고 누른다"를 가르칠 근거다.
9. **안전 장은 비밀값 하나로도 근거가 넘친다**(H-01~H-11). 순서: 넣지 않는다(.gitignore·Read 거부) → 넣으면 막힌다(푸시 보호) → 새면 먼저 교체한다.
10. **운영 장은 이슈·라벨·보드로 "다음 바퀴"를 여는 것으로 끝낸다**(G-01~G-06). `fixes` 키워드(G-02, D-07)가 기획 장과 운영 장을 잇는다. 릴리스(G-07)는 선택 심화.
